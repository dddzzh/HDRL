# Deadline归因消融解决方案：先做一个预算校准诊断，再决定是否扩展

日期：2026-10-23。

依据：[Astra交接文档](D:/研究生期间/第二篇/DRLEC/docs/ASTRA_HANDOFF_DEADLINE_CREDIT_20261023.md)、四版本已完成训练日志、现有控制器和奖励实现。

## 1. 决策

建议将新Full诊断训练的下层deadline_budget从0.08改为0.01，其他学习机制保持原值，从头训练一次SM、1200episode、seed42。先不启动四个版本。

这取代交接文档中“优先试budget=0”的候选建议。原因来自本次新增的固定训练观测序列离线分析：budget=0会让Full控制器在大量轮次饱和；0.01在该序列上既不归零也不触顶，更适合作为第一项温和干预。

当前已完成的是读代码、日志统计和离线标量计算，以及本方案文档；未修改训练配置/代码，未启动新训练或环境评估。0.01是诊断候选，不是已验证最优参数。

## 2. 研究问题与判别

- 问题：原下层预算是否使增量迟到反馈过早失去训练作用，从而影响可行性和能耗？
- 假设：缩小预算后，正的任务迟到代价能在更长训练阶段进入奖励，有机会改善策略。
- 已知：原Full第429轮起采样平均Deadline惩罚为0；Raw的非零惩罚持续更久，最终测试表现更好。
- 未知：两者之间是否为因果关系；更强惩罚是否只增加能耗；任务级代价是否本来就过小；单个训练种子的随机影响有多大。
- 支持证据：在控制其余因素的新诊断中，约束信号行为改变，既定验证协议下的能耗/可行性也改善。
- 不支持证据：仅lambda更大，验证表现无改善或退化；或者约束代价已经基本为0，归零对后期学习没有实际损失。
- 最小下一步：仅一份Full新配置、一轮完整训练。结果先用于机制诊断，不直接作为新的正式归因优势证据。

## 3. 本次新增证据：budget=0可能过强

### 3.1 计算方法

读取每个run的train_history.jsonl，保留原有逐轮low_deadline_constraint_value与low_deadline_dual_updated，使用同一PI公式：

~~~text
初始 I=lambda=1
仅原日志标记可更新的轮次执行：
    e = 原日志J - 候选budget
    I = clip(I + 0.2*e, 0, 8)
    lambda = clip(I + 25*e, 0, 8)
~~~

候选只比较0.08、0.01、0.001、0。四个run在budget=0.08下与记录的逐轮更新后乘子完全一致，最大绝对误差为0，说明计算复现了原控制器路径。

这是固定观察序列下的控制器诊断，不运行调度环境，不更新网络。真实重训会改变轨迹和J，不能把下面数值当成未来训练结果。

### 3.2 Full的离线结果

| 候选budget | 更新后lambda为0的轮数 | 更新后lambda达到上限8的轮数 | 首次达到上限的轮次 | 第1200轮更新后lambda |
|---:|---:|---:|---:|---:|
| 0.08 | 773 | 0 | 无 | 0 |
| 0.01 | 0 | 0 | 无 | 5.649853 |
| 0.001 | 0 | 266 | 393 | 7.998853 |
| 0 | 0 | 791 | 312 | 8 |

这里按“更新后”统计，因此原预算有773轮为0；此前报告的“第429—1200轮实际训练惩罚为0”是772轮。第428轮学习时乘子仍正，在轮末更新后才归零，两者没有矛盾。

对其他轨迹作相同离线计算：

| 版本 | budget=0.01时触顶轮数 | budget=0时触顶轮数 |
|---|---:|---:|
| CF-Self | 80 | 892 |
| CF-Uniform | 0 | 558 |
| Raw-Self | 720 | 1180 |

budget=0的积分项在非负代价下不会下降；它移除了“低于正预算时逐步减罚”的通道。它可以是有意设计的更严格代理目标，但不是优先选择的温和参数修正。Raw的代价语义/尺度不同，也不应依据相同数字就宣称有效惩罚强度相同。

### 3.3 只保持乘子正值还不够

用原Full日志中SAC采样任务代价均值乘以上述离线更新前lambda，得到保持原样本代价的惩罚均值估算：

| 训练阶段 | 原budget=0.08 | 候选budget=0.01 | 候选budget=0 |
|---|---:|---:|---:|
| 1—400轮 | 0.00215827 | 0.00860679 | 0.00952452 |
| 401—800轮 | 0.0000074241 | 0.00201808 | 0.00230011 |
| 801—1200轮 | 0 | 0.00011212 | 0.00014673 |

这些是固定样本均值下的估算，不是新策略的奖励或梯度。即使lambda持续为正，后期代价很小，实际作用也可能很小。因此诊断必须同时记录lambda、代价、实际惩罚，不能以“不归零”作为训练成功标准。

## 5. 诊断日志应澄清哪些量

为避免原同名字段覆盖，新增独立诊断记录时明确保存：

- episode与训练输入seed；
- dual输入工作流代价均值、CVaR观测值J、budget；
- lambda积分项、更新前/后的最终lambda；
- SAC采样任务Deadline代价均值及非零样本比例；
- 实际Deadline惩罚均值、可靠性惩罚均值；
- 基础奖励的绝对值均值或RMS（从采样张量计算），不要用正负抵消后的base_reward_mean充当尺度；
- 来源G总量、受影响者d总量、外部分配比例；只在当前归因定义内解释；
- 明确记录每轮采样更新数，区分按轮平均与按更新次数加权。

历史日志能可靠读出的量先用历史日志；缺少采样分布的部分不能事后假造。新增日志本身应通过不改变G/d、训练奖励和随机数消耗的检查。

比较“正代价存在但lambda为0”的频率，比单独统计lambda=0更直接。零代价轮次本来就不需要产生惩罚。

## 6. 一次Full诊断如何跑、如何判

训练设定沿用SM：Small科学工作流、74台服务器、每轮20工作流、旧生成口径、0.1/s、Medium Deadline、seed42、1200episode。从头联合训练上下层。

模型仍只用原两块验证池542000—542019和642000—642019选择：每20轮验证，两块ESP@90与Rel均满足原门槛时，选最低验证能耗。没有可行模型时如实结束，不自动追加轮数或更换种子。

训练过程诊断查看200、400、800、1200轮：

- lambda归零/触顶是否严重，正代价是否真正进入奖励；
- 代价和惩罚尺度是否合理；
- 有效验证模型出现时间与验证可行性；
- 在满足同样门槛前提下的验证能耗。

这些检查点用于记录，不在中途凭有利测试结果改变协议。硬件或数值异常单独处理。

判断顺序：

1. 若出现NaN、模型身份不符、输入配对错误或训练源漂移，先解决实现问题，不解释性能。
2. 若lambda仍长期饱和、代价无明显下降，说明收紧预算可能造成强惩罚/不可满足目标，不自动再降低budget。
3. 若lambda有效但验证没有改善，停止扩大重训；不能认为“再加大处罚就一定能赢”。
4. 若同样可行门槛下验证能耗改善，或可行性明确改善，再决定是否进入同协议对照。

旧训练没有完整replay可供无缝恢复，且当前消融入口拒绝resume。只加载旧权重继续训练属于另一种warm-start实验，不能冒称同起点1200轮对照。

改变评估时的下层budget不能让已训练SAC自动重学，因此不把修改测试配置作为修复办法。

## 7. 要证明“来源归因有用”，后续最少跑什么

一份新Full只能诊断预算变化；它不能单独证明来源分配的优越性。

若Full诊断值得继续，按要回答的问题扩展：

| 目标 | 需要的新增训练 | 能支持的范围 |
|---|---|---|
| 只判断收紧预算是否值得 | Full 0.01一份 | 探索性参数诊断 |
| 判断来源分配是否优于自身/均分 | 在新Full基础上，加CF-Self 0.01、CF-Uniform 0.01两份 | 同代价定义下三种分配方式的pilot |
| 保留完整四版本比较 | 再加Raw-Self 0.01一份 | 新协议四版本pilot；仍需说明Raw代价尺度不同 |

不要把新预算Full与旧预算控制组组成正式公平消融。旧四版本结果保留为原协议结果。

若要比较“扣除基线”与“原始自身代价”，优先看CF-Self与Raw-Self；Full与Raw同时改变代价定义和来源分配，不能单因素归因。

正式结果仍需承认只有一个训练seed的局限。后续训练重复应对各组对称安排；测试seed配对不替代独立训练重复。

已有测试结果已经看过。新确认性评估应在模型与协议冻结后，使用预先指定的未用配对测试输入，不按结果选择；已有测试可作探索性复核，但不能反复据其调参。

## 8. 如果用户决定完全不重训

保留既有框架和结果，将反事实部分表述为一种可解释的反馈设计，明确当前观察下未获得对Raw-Self的一致性能优势。现有结构消融支持上下层/频率/Deadline Head的作用，各自不替代来源归因证据。

现有日志可以支撑“代价定义显著影响惩罚强度与持续时间”的诊断分析；不能把这种解释当成Full优于Raw的证明。

如果最后采用Raw作为最终方法，必须同步方法定义和对应主实验，不能只更换名称或结果行。
