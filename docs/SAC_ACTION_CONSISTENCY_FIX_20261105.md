# SAC 动作一致性：问题、修复和旧结果边界

日期：2026-11-05。此次仅处理执行动作与 SAC 学习动作不一致，不调整奖励、乘子、归因、工作流、期限或基线。未启动实验训练，未修改 main2 或论文数据。

## 1. 问题到底在哪里

原路径在 `src/sac/hierarchical_low_sac.py` 中：

- `LowSACActor.sample` 在全局区间 `[rho_min, 1]` 生成频率。
- `select_frequency` 把低于当前服务器下限的频率抬到下限后执行。
- `remember_transition` 存储执行后的频率。
- `learn` 的 actor 更新和 target critic 更新，却直接使用未抬高的采样频率。

例如，策略输出 0.3，服务器下限为 0.6：环境执行 0.6，回放记录 0.6，但策略更新可能询问 Q(s, 0.3)。这并不是同一个动作。执行侧记录的裁剪率低，也不能证明训练时另外采样的动作没有越界。

这是实现问题；不能仅修改论文措辞就声称已经消除，也不能据此直接断言所有旧模型性能均失效。

## 2. 修复路径

新增显式配置 `agent.low.action_mode = "server_affine"`。令当前服务器的有效下限为 b(s)，使用：

```text
z ~ Normal(mu(s), sigma(s))
u = (tanh(z) + 1) / 2
rho = b(s) + (1 - b(s)) * u
```

同一个 `LowSACActor.sample` 被执行端、actor loss 和 target critic 共用；三处得到的都是物理频率 rho。回放仍然存储实际 rho，不把归一化变量 u 混入 critic。

对非退化区间，密度转换为：

```text
log pi_rho(rho | s)
  = log Normal(z; mu(s), sigma(s))
    - log(1 - tanh(z)^2)
    + log(2) - log(1 - b(s))
```

代码保留原有 tanh 雅可比的小量数值保护。不能只把动作映射改掉，却继续使用原固定区间的 log probability。

### 下限来源不变

b(s) 来自环境 `server_safety_metrics["rho_hardware_min"]` 与 agent 全局 rho_min 的较大者。注意环境中的该历史字段名实际是有效动作下限的别名：能效下限模式下，包含已有的 rho_ee 限制。此次不改其计算方式；不使用 rho_safe 把 deadline 可行性变成硬限制，也不新增可靠性硬裁剪。

### 回放保存服务器下限

修复模式在原低层状态末尾增加一个 b(s)，critic 也接收它。这样，回放中既有当前服务器下限，又有下一决策所选服务器的下限，不会把当前下限误用于下一动作。原 local_9 模式名称保留，但原实际 11 维状态变为 12 维。

下限转为 float32 时向上舍入至可表示值，避免数值舍入后低于真实下限。正常执行路径不再依赖越界裁剪。沿用已有的极窄区间判断：下限接近 1（1e-6 范围）时直接执行 1，并不收集策略训练样本。终止 next_state 的零向量不会进入 target actor。

### 其余训练设置

复用原 SAC loss、温度设置和优化器。当前 SM 配置的 alpha 固定为 0.2，未改为自动温度，也未调奖励或拉格朗日参数。

原 `initial_rho_mean` 仍按全局区间初始化 latent 均值；新模式实际初始频率随服务器下限变化。因此它不能再解释为“所有服务器初始频率恰好为 0.95”。这只是初始化说明，不影响三处动作映射一致。

## 3. 启用与旧模型隔离

- 未指定 action_mode 的旧配置默认 `legacy_clip`，保持原计算路径。
- 检查点保存 action_mode；旧检查点没有该字段时视为 legacy_clip。
- 新旧模式互相加载会明确报错，不允许把旧回放或旧策略直接解释为新映射。
- 旧论文结果仍属于旧实现；此次代码修复不会回溯改变它们。
- 修复模式的低层网络增加状态维度，需训练新的低层 actor/critic；若目标是新的完整层级方法结果，建议按原协议重新训练、验证和评估完整模型。仅冻结上层重训下层可以作为诊断，但不等价于完整联合训练。

已准备隔离配置 `configs/sac_action_fix_sm74_20261105.json`，相对于 `configs/v3_sm_74_legacy_train.json` **只改变两项**：

1. 新增 `agent.low.action_mode: server_affine`。
2. 输出目录变为 `results/sac_action_consistency_sm74_20261105`。

其余设置（包括 1200 轮、资源、种子、训练/验证口径）不变。此次没有启动该配置。旧的训练配置文件没有更改。

## 4. 已完成验证

可重复的小型自检：

```powershell
python -B tools/check_sac_action_consistency.py
```

10 项测试通过：动态区间和密度雅可比；执行/采样/回放相等；三种状态模式的 actor/target/replay critic 输入；全终止批次；固定频率区间；非法下限；非法回放；新检查点往返加载；新旧模式拒绝混载；旧采样公式保持不变。

另与修改前 git HEAD 中的实现逐项比较：三种旧状态模式下，采样动作、诊断值、一次梯度更新的所有指标和网络参数均逐位相同。当前论文 SM74 的旧检查点也已只读加载成功。

这些是代码一致性检查和小型内存梯度测试，**不是性能实验**。尚未验证新模式的收敛、ESP、可靠性达标率、能耗或跨种子稳定性，不承诺修复后性能一定更好。

## 5. 此阶段的结论

实现层面的新路径已统一动作语义；历史实验并未因此成为新实现的实验。下一步应先用隔离 SM 配置验证训练是否正常，再根据结果决定是否替换论文方法及数据，不能直接用新公式描述旧检查点。
